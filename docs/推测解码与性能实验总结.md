# 推测解码与性能实验总结

> 本文合并 MTP/DFlash 原理、Qwen3.8 提速实验和各平台推测解码记录。
> 结论优先级：正确率与正确答案耗时 > 端到端速度 > acceptance rate。

## 1. 当前结论

| 平台与模型 | 配置 | 记录结果 | 定位 |
| --- | --- | ---: | --- |
| 231 RTX 5090，Qwen3.6-35B-A3B-NVFP4 | 单卡、MTP@4、20K | **约 400 tok/s** | 2026-09-20 当前最快部署记录 |
| 231 RTX 5090，Qwen3.8-27B-NVFP4 | 单卡、MTP@3、32K、eager | **40+ tok/s** | 2026-09-20 当前服务记录 |
| 231 RTX 5090，Qwen3.8-27B-NVFP4 | 单卡、MTP@3、20K、CUDA Graph | 67.2 tok/s | 2026-08-20 历史固定题实验 |
| 双 RTX 5090，Qwen3.6 + DFlash | TP=2、k=10、10K | 327.05 tok/s | 历史 DFlash 标杆 |
| RTX PRO 6000，Qwen3.6 + DFlash | 单卡、k=10 | 178.69 tok/s | 历史平台对照 |

这些数字来自不同日期、模型、请求长度和统计口径，只能说明各自配置已经达到的量级，不能直接用来宣布模型质量或严格性能排名。下一轮应使用同一题集、采样参数和客户端计时统一复测。

## 2. MTP 与 DFlash

| 项目 | 内置 MTP | DFlash |
| --- | --- | --- |
| draft 来源 | target checkpoint 内置多 token head | 独立训练的 draft checkpoint |
| 配置 | `method=mtp`，通常不写 `model` | `method=dflash`，必须给 draft 路径 |
| 工程复杂度 | 低，适合部署第一条投机基线 | 高，需保证 target/draft/runtime 匹配 |
| 主要调参 | speculative token 数、acceptance、显存 | block/k、anchor、draft backend、状态缓存 |
| 适合目标 | 快速建立稳定低延迟服务 | 追求更高性能上限 |

Qwen3.8 MTP 示例：

```bash
--speculative-config '{"method":"mtp","num_speculative_tokens":3}'
```

DFlash 示例：

```json
{
  "method": "dflash",
  "model": "/data/metahuman_work/models/Qwen3.6-35B-A3B-DFlash",
  "num_speculative_tokens": 10
}
```

投机解码仍由 target 验证候选 token；理论上不应改变目标分布，但工程版本、采样和实现差异仍需通过 Pass@1 实测确认。

## 3. Qwen3.8 单卡提速过程

2026-08-19 至 2026-08-20 的历史实验：

| 阶段 | eager | MTP | 窗口 | `max-num-seqs` | 结果 |
| --- | --- | --- | ---: | ---: | ---: |
| no-spec 基线 | 是 | 无 | 32K | 默认 | 9.4 tok/s |
| 官方 MTP 基线 | 是 | 3 | 32K | 默认 | 24.7 tok/s |
| CUDA Graph | 否 | 3 | 10K | 1 | 67.8 tok/s |
| CUDA Graph 最终版 | 否 | 3 | 20K | 1 | 67.2 tok/s |

已闭环的判断：

1. no-spec 慢的主因是 eager 下混合 GDN 的小 kernel launch 开销，生成时 GPU 利用率曾只有约 20%。
2. MTP@3 把 eager 基线从 9.4 提高到 24.7 tok/s，mean acceptance length 为 3.19/4。
3. 把窗口从 32K 降到 10K、但仍保留 eager，速度没有改善；因此窗口不是当时 decode 慢的主因。
4. 去掉 eager 并限制 `max-num-seqs=1` 后，CUDA Graph 池只约 0.06 GiB，速度提升到约 67 tok/s。
5. 10K 扩到 20K 后速度基本不变，20K 因截断风险较低成为当时的单请求候选。

2026-09-20 的当前 Qwen3.8 记录为 40+ tok/s，采用 32K、eager、MTP@3、Text Only。它与上面的历史 Graph 实验不是同一配置和口径，应保留两条记录，不能用其中一个覆盖另一个。

## 4. 显存与失败经验

- 32GB 单卡加载 Qwen3.8 NVFP4 + MTP 曾需要约 30.5 GiB 空闲显存；其他服务占用约 0.86 GiB 就会导致 OOM。
- `gpu-memory-utilization` 不是“凭空增加物理显存”；物理空闲不足时把 0.95 改成 0.98 也无法解决问题。
- 去 eager 时默认 Graph capture 规模可能挤占 KV Cache；单请求业务用 `max-num-seqs=1` 是已验证的关键手段。
- OOM 调整顺序应固定：清点其他进程 → 稳定 eager 基线 → 降并发 → 降上下文 → 关 MTP。
- 共享 GPU 上停止其他人的容器必须先协调，资源占用本身也要写入实验记录。

## 5. DFlash 历史结论

双 RTX 5090 的 vLLM + DFlash 记录：

| 参数 | k=5 | k=10 |
| --- | ---: | ---: |
| 客户端 Decode TPS | 268.49 | **327.05** |
| 相对提升 | 基线 | +21.81% |

RTX PRO 6000 的记录中，k=10 约 178.69 tok/s。双 5090 即使没有 NVLink，在该 workload 下仍更快。SGLang + DFlash 曾跑通约 66.98 tok/s，但配置没有与 vLLM 对齐，不能据此判断引擎上限。

`k` 越大不保证越快。窗口增加会提高一次验证能接受的 token 上限，也会增加 draft 和 verify 开销。最优值只能通过端到端耗时实测确定，不能只看 acceptance rate。

## 6. 采样、thinking 与测量口径

Qwen3.8 的历史默认采样为：

```text
temperature=1.0, top_k=20, top_p=0.95
```

正式 A/B 必须显式固定。历史 vLLM 响应的思考内容在 `message.reasoning`，最终答案在 `message.content`。短输出受 TTFT 影响很大，几百 token 的平均 TPS 波动不能代表稳态 decode。

每条结果至少记录：

```text
机器/GPU、镜像 digest、runtime 与 CUDA 版本
target/draft checkpoint 与量化格式
上下文、并发、KV dtype、eager/graph、spec 方法与 k
提示 token、输出 token、采样参数、thinking 设置
TTFT、Decode TPS、端到端耗时、finish_reason
Pass@1、截断、显存、GPU util、acceptance 指标
```

## 7. 决策原则

1. 生产候选先过正确率门槛，再按 Time-to-correct 排序。
2. acceptance rate、服务端吞吐和峰值 TPS 都是解释变量，不是最终目标。
3. 一次实验只回答一个问题，不能同时换模型、镜像、backend、上下文和 k。
4. 当前优先复现 2026-09-20 两条服务记录，再用统一数学题集比较 Qwen3.6 与 Qwen3.8。
