# 数学测试台前后端开发路线图

## 1. 项目目标与边界

数学测试台用于管理数学题库、发起单题或批量解答、展示公式与思考过程、保存运行历史，并支持人工评价和后续统计分析。

本路线图只覆盖 Web 前端、业务后端、MongoDB 数据、测试与应用可观测性，不包含模型安装、镜像制作、推理引擎启动、GPU 调优或模型服务器部署。

固定产品边界：

- 前后端使用 TypeScript。
- 解题固定使用思考模式，思考过程独立保存、默认折叠。
- 不引入 TIR、代码执行器或工具调用循环。
- 参考答案不发送给解题接口。
- MongoDB 是运行时唯一业务数据源，题目原图继续使用文件存储。
- 当前按单活动任务设计；增加队列后也先保持并发为 1。

## 2. 当前基线

### 已完成的前端能力

- 题目列表、搜索、分类与难度筛选，以及刷新后恢复当前题目。
- 模型配置的新增、编辑、联动选择和持久化。
- 单题启动、停止、实时状态、思考过程折叠与正式答案流式展示。
- LaTeX/Markdown 渲染，题目、回答、参考答案原始 Markdown 复制。
- 解题期间允许浏览其他题目，同时保证只有活动题可以停止。
- 题目与参考答案原图预览。
- 历史运行查看、运行指标展示、人工评价与备注。

### 已完成的后端能力

- Fastify API 与 SSE 流式输出。
- 题库、运行历史、模型配置、当前选择和人工评价保存到 MongoDB。
- 每次运行保存题干、参数、模型配置快照、思考、正式答案、usage 和耗时。
- 单活动任务约束、手动取消、请求超时和异常状态分类。
- 浏览器刷新或断开后，任务继续执行并保存；页面可重新获取活动任务。
- 运行过程中定期写入检查点，服务重启后将遗留运行标记为中断。
- 后台串行批量脚本：每题只提交一次，失败或截断后继续下一题。

### 当前主要限制

- 前端主页面承担了过多状态和业务逻辑，组件边界不够清晰。
- `/api/runs` 一次返回全部历史，题量和运行次数增加后会变慢。
- 活动任务保存在单个 Node 进程内，后端重启不能继续原任务。
- 批量测试只有命令行脚本，没有页面管理、暂停、恢复和进度统计。
- 题库仅支持迁移导入，缺少日常管理、质量标记和版本记录。
- 缺少自动评分、批次统计、结果对比与数据导出。
- API 缺少统一契约、结构化错误码和完整的接口级测试。
- 当前面向个人使用，没有账号、权限和操作审计。

## 3. 目标架构

```text
React 页面
  ├─ 题库与题目详情
  ├─ 单题测试与运行详情
  ├─ 批次管理与结果统计
  └─ 配置与数据导出
          │ HTTP / SSE
Fastify API
  ├─ questions 题库服务
  ├─ runs 单题运行服务
  ├─ batches 批次与队列服务
  ├─ reviews 人工评价服务
  └─ model-configs 连接配置服务
          │
MongoDB
  ├─ questions
  ├─ runs
  ├─ batches / batch_items
  ├─ model_configs / model_settings
  └─ audit_logs（多人使用时）
```

原则是让“任务生命周期”由后端管理，浏览器只负责订阅和展示。前端刷新、切页或临时断网不应改变任务状态。

## 4. 分阶段路线

### P0：整理现有基线

目标：让当前版本的行为、文档和测试保持一致，为后续拆分建立稳定基线。

前端：

- 拆分 `main.tsx`，至少形成题库侧栏、题目详情、运行面板、历史列表和评价面板。
- 把服务端数据请求集中到 API 客户端模块，统一错误解析和取消逻辑。
- 明确页面状态：当前题目、当前查看的历史、活动任务和选中模型互不混用。
- 修正文档中“刷新会取消运行”等已经过期的描述。

后端：

- 将路由、业务服务和 MongoDB Store 从 `index.ts` 分层。
- 为请求参数和响应增加运行时校验，避免只依赖 TypeScript 类型。
- 统一错误结构，例如 `{ code, message, details? }`，前端按错误码提示。
- 给活动任务增加阶段快照，使刷新后能准确恢复 waiting、thinking、answering 状态及阶段计时。

验收：

- 现有浏览器交互不变。
- 类型检查、单元测试、MongoDB 集成测试、生产构建全部通过。
- 刷新恢复、手动停止、切题浏览和历史评价均有稳定回归测试。

### P1：历史查询与运行详情

目标：历史数据增长后仍能快速定位和分析某次运行。

前端：

- 增加独立运行详情视图，支持通过 URL 直接打开指定题目和 runId。
- 历史列表支持状态、时间、模型、评价筛选及分页。
- 同一道题支持选择两次运行并排比较答案、耗时、token 和参数。
- 增加 JSON、Markdown 导出；批量导出使用异步任务或流式下载。

后端：

- 将运行 API 改为分页：`GET /api/runs?questionId=&status=&cursor=&limit=`。
- 增加 `GET /api/runs/:id`，避免前端为了一个详情读取全部历史。
- 补充组合索引，并通过 `explain` 验证常用查询。
- 明确运行记录不可变字段与可编辑字段；人工评价单独更新并记录更新时间。

验收：

- 在至少一万条运行记录下，题目历史首屏查询仍保持可接受响应时间。
- 刷新或复制详情地址后，可恢复同一题目与同一次运行。
- 导出内容与数据库快照一致，不包含凭据。

### P2：批量测试产品化

目标：把当前后台脚本升级为可观察、可恢复的业务任务。

前端：

- 提供新建批次页面：选择题目范围、固定生成参数和模型配置。
- 展示总数、待运行、进行中、完成、截断、失败、取消的实时统计。
- 支持暂停后不再领取下一题、恢复、停止当前题和终止剩余任务。
- 失败项可筛选和导出；默认不自动重试，重跑必须由用户明确创建新运行。

后端：

- 新增 `batches` 与 `batch_items`，持久化题目快照、参数快照、顺序和状态。
- 使用数据库原子领取任务，并保持并发为 1。
- 批次调度与浏览器连接解耦；服务重启后从数据库恢复未完成批次。
- 每个题目只创建一个明确关联的 runId，批次汇总不复制完整答案。
- 增加批次事件或轻量轮询接口，避免每两秒读取全部 runs。

验收：

- 创建批次后关闭页面，任务仍继续；重新打开可看到准确进度。
- 单题失败后记录失败并继续下一题，不发生隐式重试。
- 暂停、恢复和终止在服务重启后语义一致，不产生重复运行。

### P3：评测与统计

目标：从“保存答案”升级为“可比较的数学评测工作台”。

前端：

- 增加批次统计页：完成率、截断率、失败率、人工正确率和待复核数。
- 展示首响应、思考耗时、总耗时、输出 token 的分布，而不只展示平均值。
- 按题型、难度、模型配置、参数和时间范围交叉筛选。
- 提供错题与截断题工作台，便于逐题复核和填写备注。

后端：

- 增加聚合统计 API，并保留原始 runId 以便追溯。
- 记录提示词版本、应用版本和批次来源，保证结果可复现。
- 先实现规则型答案规范化与辅助比较；自动评分结果必须与人工评价分开存储。
- 证明题和复杂解答只提供辅助评分，不能直接覆盖人工结论。

验收：

- 任意统计数字都能下钻到对应运行记录。
- 自动评分、参考答案质量问题、输出截断和接口失败能够分别统计。
- 同一批次的参数与题目集合在创建后不可被配置修改污染。

### P4：题库与数据治理

目标：建立可持续维护的数据闭环。

前端：

- 增加题目管理页，支持查看与修订题干、参考答案、标签和难度。
- 增加缺图、OCR 疑似错误、答案不完整、题目需复核等质量标记。
- 原图查看支持缩放、旋转和题目/答案图片快速切换。

后端：

- 题目修订使用版本或修订记录，不直接覆盖历史运行所依据的题目快照。
- 导入提供预检报告：新增、重复、冲突、缺图和格式错误数量。
- 增加数据备份校验和恢复演练说明，覆盖 MongoDB 与图片文件。
- 建立归档策略，避免业务集合和页面无限增长。

验收：

- 每次题目修订可追踪操作者、时间、旧值与新值。
- 历史运行仍能显示运行当时的题干与参考版本。
- 导入失败不会留下半完成数据。

### P5：多人使用与应用可靠性

目标：在需要共享使用时补齐权限、安全和可观测性。

前端：

- 增加登录态、权限提示和当前用户信息。
- 区分浏览、运行、评价、题库管理和系统配置权限。
- 对长任务、断网重连和后台错误提供明确通知。

后端：

- 增加认证、角色权限、CSRF/来源策略和操作审计。
- 对创建运行、批次和配置修改增加限流及幂等键。
- 健康检查拆分为存活与就绪检查；日志统一带 requestId、runId、batchId。
- 增加关键指标：API 错误率、数据库延迟、活动任务、队列长度和任务耗时。
- 将单进程内存锁升级为数据库租约或可靠队列，避免多个后端实例重复领取任务。

验收：

- 未授权用户不能读取思考内容、修改配置或启动任务。
- 重复点击、网络重发和多实例竞争不会创建重复任务。
- 每次用户操作和任务异常都能通过日志与 ID 完整追踪。

## 5. 测试路线

测试随每个阶段同步建设，不作为最后补做事项。

- 单元测试：公式规范化、SSE 解析、参数校验、状态转换、统计计算。
- Store 集成测试：MongoDB 索引、分页、原子领取、幂等与恢复。
- API 测试：正常响应、结构化错误、取消、断流、超时和权限边界。
- 浏览器测试：筛选、运行、刷新恢复、切题、停止、复制、评价、批次管理。
- 回归数据：固定少量题目与模拟流，测试不得依赖真实外部解题服务。
- 真实冒烟：只用于人工验收，不替代确定性的自动化测试。

持续集成的最低门槛：

```bash
npm run check
npm test
npm run build
```

涉及 MongoDB Store 变更时，再运行：

```bash
npm run test:mongodb
```

## 6. 推荐实施顺序

建议按 `P0 → P1 → P2 → P3 → P4` 推进。P5 在应用准备给多人使用前完成。

近期最值得优先完成的三个里程碑：

1. 拆分前后端结构，并补齐活动任务阶段快照和统一错误协议。
2. 完成运行历史分页、详情 URL 和同题结果对比。
3. 将串行批量脚本产品化为持久化批次队列与页面进度管理。

这三个里程碑完成后，项目会从个人单题验证工具升级为具备稳定任务管理、结果追溯和批量评测能力的数学测试平台。
