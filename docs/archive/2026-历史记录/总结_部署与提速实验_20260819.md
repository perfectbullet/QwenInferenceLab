### 实验 1：no-spec 基线（官方配方）

**配置**：`--enforce-eager --max-model-len 32768 --kv-cache-dtype fp8 --gpu-memory-utilization 0.95`，无投机解码。

**启动命令**：

```bash

  -v /nfs-data/metahuman_work/models/Inferact/Qwen3.8-27B-NVFP4:/model \
  -p 8000:8000 \
  --restart unless-stopped \
  vllm/vllm-openai:qwen38 \
  --model /model \
  --served-model-name qwen38-27b \
  --tensor-parallel-size 1 \
  --max-model-len 32768 \
  --kv-cache-dtype fp8 \
  --gpu-memory-utilization 0.95 \
  --enforce-eager \
  --reasoning-parser qwen3 \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder
```

（此容器现保留为 `vllm-qwen38-nospec`。）

**结果**：
- ✅ 启动成功（约 5 分钟，NFS 加载占大头），数学冒烟答对。
- ❌ **速度仅 9.4 tok/s**，用户实测一道题 342 秒且输出为空，基本不可用。

**诊断证据链**：

| 证据 | 数值 | 含义 |
|---|---|---|
| 引擎 decode 吞吐 | 9.3~9.6 tok/s | 比理论（80~120）慢约 10 倍 |
| GPU 利用率 / 功耗 | 20% / 135W（满载 ~600W） | GPU 在等，不是在算 |
| 冒烟实测 | MATH-248 耗时 342s、输出空 | 不可用 |

**根因**：
1. **主因：`--enforce-eager` 关闭 CUDA Graph**。混合 GDN 架构每 token 串行发起几十个小 kernel（conv1d_update、gated_delta_rule、mrope、layernorm……），eager 模式下 launch 开销完全主导。
2. MTP 未启用，每 step 只出 1 token。
3. 死路排除：`VLLM_QWEN3_5_GDN_DECODE_KERNEL=fused` 要求 SM100（B200 级），5090 是 SM120 用不了（源码 `_validate_fused_gdn_decode_kernel` 确认）。

### 实验 4：窗口归因对照实验（验证"慢是否因 32768 窗口"）

**背景**：用户质疑 §五.1 的归因——"官方配方慢也许主要是 `--max-model-len 32768`，而非 eager"。当时 24.7→67.8 之间同时改了三个变量（去 eager、窗口 32K→10K、num-seqs→1），归因确实不纯净，值得单独隔离验证。

**实验设计**：与实验 2④（24.7 tok/s 配置）**只差一个变量**——窗口 32768 → 10240，eager 保留、num-seqs 保持默认。

**启动命令**：

```bash
docker run -d --gpus all --name vllm-qwen38 \
  -e PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True \
  -v /nfs-data/metahuman_work/models/Inferact/Qwen3.8-27B-NVFP4:/model \
  -p 8000:8000 \
  --restart unless-stopped \
  vllm/vllm-openai:qwen38 \
  --model /model \
  --served-model-name qwen38-27b \
  --tensor-parallel-size 1 \
  --max-model-len 10240 \
  --kv-cache-dtype fp8 \
  --gpu-memory-utilization 0.95 \
  --enforce-eager \
  --reasoning-parser qwen3 \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder \
  --speculative-config '{"method":"mtp","num_speculative_tokens":3}'
```

**结果（2026-08-20 01:42 实测，同一道题）**：

| 指标 | 数值 |
|---|---|
| 客户端速度 | **19.9 tok/s**（13.6s / 271 tokens） |
| 引擎稳态吞吐 | 22.5 tok/s |
| MTP 接受长度 | 3.24 |
| 答案正确 | ✅ `\boxed{3}`，finish_reason=stop |

**结论：假设不成立**。完整对照矩阵：

| 配置 | eager | 窗口 | num-seqs | 客户端/引擎速度 |
|---|---|---|---|---:|
| A（实验2④） | ✅ | 32K | 默认 | 24.7 tok/s（引擎） |
| **B（本实验）** | ✅ | **10K** | 默认 | **19.9 / 22.5 tok/s** |
| C（实验3⑥） | ❌ | 10K | **1** | **67.8 tok/s（客户端）** |

- A → B 只改窗口：速度不变（同档）→ **`max-model-len` 不是 decode 速度因子**（它只决定 KV cache 分配多大，不影响每 token 计算路径）。
- B → C 去 eager + num-seqs 1：**3 倍差距** → 慢的主因确认为 enforce-eager（kernel launch 开销），归因闭环。
- B 略慢于 A 属正常波动（引擎统计窗口与 TTFT 占比差异）。

**实验后处置**：删除实验容器，已恢复 C（最快配置）为 `vllm-qwen38` 并确认就绪。

### 实验 5：窗口扩到 20K（当前最终配置）

**动机**：10K 配置的最大风险是截断（题面 + `max_tokens=8192` 余量紧张）。实验 4 已证明窗口不是速度因子，那么能否用 20K 消掉截断风险、同时保住 CUDA Graph 速度？

**插曲**：首次尝试时 chenna 同事的 Paddle-VL 服务（2 × `async_services.main`，共 17.3 GiB）恰好上线，GPU 空闲仅 13.9 GiB，实验无法启动；经协调暂停其服务后重试成功。**教训：共享 GPU 的显存预算随时可能被其他负载打破，重要实验前先 `nvidia-smi` 核对。**

**启动命令（当前生效）**：

```bash

  -e PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True \

  -p 8000:8000 \
  --restart unless-stopped \
  vllm/vllm-openai:qwen38 \
  --model /model \
  --served-model-name qwen38-27b \
  --tensor-parallel-size 1 \
  --max-model-len 20480 \
  --max-num-seqs 1 \
  --kv-cache-dtype fp8 \
  --gpu-memory-utilization 0.95 \
  --reasoning-parser qwen3 \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder \
  --speculative-config '{"method":"mtp","num_speculative_tokens":3}'
```

与 10K 最快配置唯一差异：`--max-model-len 20480`。

**结果（2026-08-20 实测）**：

| 测试 | 结果 |
|---|---|
| 标准数学题（同题对比） | **67.2 tok/s**（3.9s/261 tokens）——与 10K 版 67.8 同速，**零速度损失** |
| 长输出压力（max_tokens=12288，ignore_eos） | **131.5 tok/s** 稳态（93.5s 完成 12288 tokens） |
| KV cache | 37,302 tokens（20,480 窗口的 1.82x 冗余） |
| CUDA graph 池 | 0.06 GiB（不变） |
| 截断风险 | 基本解除：题面 + 8192 输出余量充足 |

**最终配置矩阵**：

| 配置 | eager | 窗口 | 速度（标准题） | 长输出稳态 | 截断风险 |
|---|---|---|---:|---:|---|
| 官方配方 + MTP | ✅ | 32K | 24.7 tok/s | ~25 | 无，但太慢 |
| graph + 10K | ❌ | 10K | 67.8 tok/s | — | **高** |
| **graph + 20K（最终）** | ❌ | 20K | **67.2 tok/s** | **131.5 tok/s** | **低** |

**结论**：20K 是当前 32GB 单卡的最优平衡点——速度与 10K 持平、窗口翻倍、截断风险基本消除。已作为生产候选配置。

### 实验 6：思考模式验证（更正一个重要误读）

**背景**：此前所有测试中"思考段为空"的记录是**误读**——这个 vLLM 版本把思考文本放在响应的 `message.reasoning` 字段（OpenAI 新命名），而非 `reasoning_content`；读错字段名导致一直显示为空。

**模板真相**（读取 `chat_template.jinja` 确认）：
- `enable_thinking` **不传即默认 true**——**服务从第一天起就一直在思考模式（xhigh）下运行**，此前所有速度数据都是"含思考"的真实成绩；
- `reasoning_effort` 支持 `xhigh`（默认）/ `medium` / `low`；
- 显式关闭：`chat_template_kwargs: {"enable_thinking": false}`（模板会注入空 `<think></think>`）。

**实测（2026-08-20，20K 最终配置，显式 xhigh）**：

| 测试 | 输出 | 思考占比 | 速度 | 正确性 |
|---|---|---|---:|---|
| 简单题（同题 f(x)=x³-3x+1） | 348 tokens（思考 536 字 + 正文 181 字），3.1s | ~60% | **111.8 tok/s** | ✅ |
| 难题（递推数列 a_{n+1}=2a_n+n 求通项+证明） | 1497 tokens（思考 2158 字 + 正文 802 字），13.5s | **72.9%** | **111.2 tok/s** | ✅ `a_n=3·2^{n-1}-n-1` |

**关键更正与结论**：
1. 思考模式的**持续输出速度 ≈ 111 tok/s**（两道题独立测得 111.8 / 111.2，高度一致）。此前"标准题 67 tok/s"是短输出下 TTFT 摊薄的统计噪声，不是思考模式降速。
2. 速度口径修正：短题（几百 token）整体 ~67-112 tok/s（TTFT 占比大）；长思考题 ~111 tok/s；超长压满 131.5 tok/s。**对高考数学（思考占比 70%+ 的难题），真实体验约 111 tok/s——一道 4000 token 的难题约 36 秒**。
3. 思考文本是英文（"We need answer in Chinese..."），正文按指令输出中文——这是 Qwen 思考链的正常行为，不影响正则提取 `\boxed{}`（在 content 字段）。
4. 对评测脚本的启示：提取最终答案用 `message.content`；统计思考量用 `message.reasoning`（注意不是 `reasoning_content`）。

### 实验 7：评测脚本改造与预算标定（2026-08-20）

**改动**（`math_eval_pipeline/tir_math/run_model_tir_inference_concurrent.py`）：

| 项 | 内容 |
|---|---|
| 采样参数 | 按 [ModelScope 官方](https://modelscope.cn/models/Qwen/Qwen3.8-27B) Thinking 模式推荐显式固定：`temperature=1.0, top_p=0.95, top_k=20`（CLI 可覆盖，写入 metadata） |
| COT 直连 | 绕过 qwen_agent（其 0.0.34 丢弃 `delta.reasoning`），openai SDK 流式直连 → 真实 TTFT / prompt+completion tokens（usage 口径）/ finish_reason / decode_tps / reasoning_chars |
| TIR 路径 | 保留 agent（工具调用需要）；加 TTFT 与字符近似 token（`tokens_source=approx_chars_no_reasoning` 注明口径）；**effort 无法传递**（openai SDK 拒绝顶层 `chat_template_kwargs`，agent 只搬 top_k/repetition_penalty），实际为模型默认 xhigh，metadata 记 `reasoning_effort_effective` |
| `--reasoning-effort` | 默认 medium，经 `extra_body.chat_template_kwargs` 生效（已验证） |
| `--max-tokens` | 默认 4096（用户决策） |

> **澄清（2026-08-20）**：用户此前"就用 2k 吧"实为 **20K 之笔误**（指服务端窗口 20480，当时已生效）。但因此触发的预算实测仍有价值：确认了 2048 客户端预算会截断思考题、4096 是当前平衡点。服务端 20K 窗口 + 客户端 4096 输出预算的组合维持不变。
| `final_answer_raw` | `\boxed{}` 提取（支持嵌套括号） |
| `truncated` | 三重判定：finish=length ∨ tokens≥预算 ∨ 有输出无 boxed |
| 横幅告警 | xhigh + <4096 预算时打印截断风险提示 |

**验证**：MATH-233 完整跑通（2168 tokens，答案 "B" 提取成功，TTFT 0.2s，decode_tps 109）。

**预算标定实测**（同一道题扫参数）：

| 题目 | 配置 | tokens | 结果 |
|---|---|---|---|
| 椭圆弦长（单问） | 2048+low / medium | 2013 / 1901 | ✅ 均完成 |
| MATH-233（选择） | 2048~4096+medium | 1667~2168 | ✅ 完成 |
| **MATH-247/248（多问综合）** | 2048~8192 任何 effort/温度 | **全部撞顶** | ❌ 思考反刍循环 |

**关键发现——思考反刍（rumination loop）**：MATH-247/248 这类多问大题，思考尾部呈"Not right. Hmm, let me try… doesn't help. Actually, let me re-examine…"的无限重推模式，思考量随预算膨胀（2048→4096→8192 全部烧光，最多 17277 字符）；关闭思考后正文又超长（6342 字符仍无 boxed）。**这是模型在难题上的真实失败模式，与预算无关**——基准应如实记录（truncated→判错），不为单题调参。冒烟/校准跑完后用 truncated 字段统计截断率，再决定是否整体调预算或 effort。

## 五、经验沉淀

1. **"官方配方慢"不一定是官方错**——RTX 5090 单卡的官方 NVFP4 配方默认 eager 是为了避开 capture OOM，代价是 GDN 架构的 launch 开销；用 `--max-num-seqs 1` 把 capture 缩到 bs=1 后，graph 的显存代价几乎消失（0.06 GiB），两全其美。**该归因已经实验 4 对照闭环验证**：eager 下把窗口从 32K 降到 10K 速度不变（22.5 vs 24.7 tok/s），去掉 eager 后 3 倍提速——慢的主因是 eager，不是 `--max-model-len 32768`。
2. **OOM 排障先算物理账**：三次 OOM（差 70 MiB、差 10 MiB）说明 32GB 单卡跑 27B + MTP 已贴物理极限，任何参数微调都不如"腾出别人的 0.86 GB"管用。
3. **共享 GPU 是部署变量**：显存预算必须按"其他容器实际占用"动态核算，不是文档里写的理论值。
4. **速度诊断三件套**：引擎吞吐日志 + 生成中的 GPU util/功耗 + 客户端计时，三者对齐即可定位是"算力瓶颈"还是"调度/launch 瓶颈"（本次 20% util / 135W 直接锁定后者）。
5. **提速实验的验收永远是正确性**：三次配置跃迁每次都用同一道题验证 `\boxed{}` 答案，速度数据才有意义。
6. **"字段为空"先怀疑字段名，再怀疑行为**：思考段"一直为空"的真相是 `reasoning` vs `reasoning_content` 的命名差异（vLLM 版本间不兼容），险些据此得出"模型没思考"的错误结论。涉及"缺失/为空"的判断，先 dump 原始响应看字段全貌。
7. **短输出的平均速度是噪声**：几百 token 的请求 TTFT 占比过大，速度数字在 67~112 之间跳动；要测真实 decode 速度，要么用长输出压满（131.5），要么用长思考题（111），两个口径互相印证。
