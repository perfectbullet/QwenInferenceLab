# 下一阶段推理部署与推测解码路线图（归档）

> 生成日期：2026-08-18
> 适用环境：231 服务器（RTX 5090 32GB）；另有双 RTX 5090 测试环境。
> 目标：在**不降低高考数学题正确率**的前提下，把单请求端到端解题时间压到最低；同时形成可量化分析、调优和复现的推理系统能力。

---

## 1. 已建立的性能基线

### 1.1 当前主基线：不可丢失

| 硬件 | Runtime | Target / Draft | 并行与投机 | Workload | 客户端 Avg Decode TPS |
|---|---|---|---|---|---:|
| 2 × RTX 5090 32GB | vLLM 0.26.0 | Qwen3.6-35B-A3B-AWQ-4bit / DFlash | TP=2，k=10 | 单请求、长思考、10K 上下文 | **327.05** |

这是后续实验的主要性能标杆。任何新方案都应以同一 workload 与该结果比较，而不是只报告服务端吞吐或单次峰值。

### 1.2 已验证结论

1. DFlash 的优化目标是最终 Decode TPS，不是最高 acceptance rate。
2. k=10 比 k=5 更快：双 5090 上从 268.49 提升到 327.05 tok/s（+21.81%）。
3. 双 5090 的 TP=2 即使没有 NVLink，当前 workload 下仍明显优于单张 RTX PRO 6000。
4. SGLang + DFlash 已跑通，但现有 66.98 tok/s 与 vLLM 的 327.05 tok/s 并非同等参数比较，不能视为 SGLang 的性能上限。

## 2. 下一阶段的主目标

### 主线 A：完成 SGLang + DFlash 的可归因性能诊断（最低优先级）

当前不把这条线当作主要投入方向。现有 SGLang + DFlash 结果与 vLLM 基线差距较大，而且没有充分证据表明问题值得立刻深挖。只有在 vLLM 主线稳定、或需要验证 SGLang 的特定能力时，才回头做可归因诊断。

要把 vLLM 与 SGLang 拆成下面四层逐项对照：

| 层级 | 需要对齐或记录的内容 |
|---|---|
| Workload | 同一提示集、输入长度、输出上限、采样参数、thinking 开关、并发数 |
| 模型 | 同一 target/draft 权重、相同 TP=2、相同量化版本 |
| Runtime | attention backend、CUDA Graph、prefix cache、async scheduling、batch / prefill 设置 |
| 投机解码 | k / block size、acceptance length、各位置接受率、draft 与 verify 时延 |

优先验证的假设：

1. SGLang 现用 Triton，而 vLLM 使用 FlashAttention；attention backend 可能是主要差异来源。
2. SGLang `k=16` 与 vLLM `k=10` 不可直接比较，应该先扫相同或相邻的窗口。
3. SGLang 的 `--mem-fraction-static 0.70`、`--cuda-graph-max-bs-decode 2`、Mamba cache strategy 可能为稳定性而牺牲了单请求性能。
4. Qwen 混合 GDN 模型除了 KV cache 还有 recurrent/Mamba state；状态池精度、大小和调度策略必须单独测量，不能只盯 KV cache。

### 主线 B：把 Qwen3.8-27B 做成高考数学单请求主实验平台（最高优先级）

Qwen3.8-27B 的价值不只是新模型：它是混合 GDN + 原生 MTP + 视觉/视频 + reasoning/tool calling 的组合，适合把你已经掌握的 DFlash 经验扩展成更通用的推理系统能力。

建议将它分成两条清晰路线，不混测。其中 vLLM 是当前主线；SGLang 仅作为后续备选。

| 路线 | 首要目标 | 推荐引擎与投机方式 |
|---|---|---|
| 当前主线：单请求数学 | 高考数学题的正确答案时间最短 | **vLLM + 内置 MTP；后续可验证 DFlash** |
| 后续备选：SGLang | 比较 DSpark / GDN 调度优势 | Low-Latency 配方；非当前优先级 |

**不要在第一轮就假设 Qwen3.8 有可用的 DFlash draft checkpoint。** 只有确认存在与当前 runtime 兼容的 Qwen3.8 DFlash draft 后，才将 DFlash 加入 Qwen3.8 矩阵。

## 3. 实验路线与完成标准

### Phase 0：冻结现有基线（1 次）

目标：以后每次升级镜像、FlashInfer、CUDA 或模型时，都能判断性能是变好还是变坏。

- 固化 vLLM 最佳启动命令、完整容器镜像 digest、GPU 驱动、CUDA、vLLM、FlashInfer/Cubin 版本。
- 固化测试提示集：短推理、长数学思考、工具调用各至少 10 条。
- 每条记录：TTFT、客户端 Decode TPS（avg / P50 / P90 / P95 / P99）、总输出 token、端到端时长。
- 服务端额外记录：accepted/drafted token、mean acceptance length、每位置接受率、显存、GPU util、功耗。

完成标准：重复运行 3 次，Avg Decode TPS 波动不超过 5%，否则先排除测试噪声。

### Phase 1：Qwen3.8 + vLLM 数学基线与 MTP（最高优先级）

固定：231 单张 RTX 5090、单请求、中文高考数学题集、Pass@1、同一 prompt、同一采样参数和同一最大输出长度。

建议顺序：

1. 下载并使用 `Inferact/Qwen3.8-27B-NVFP4` 建立 COT 与 TIR 的 no-spec 基线；它是 vLLM 官方单张 RTX 5090 NVFP4 配方的 target。
2. 在相同配置下启用模型内置 MTP（先从 `num_speculative_tokens=3` 开始）。
3. 只保留 Pass@1 不低于 no-spec 基线、且 Time-to-correct 更短的配置。
4. 评估 8K、20K、32K 服务窗口，确认最大输出 8192 时不发生截断或 OOM。

### Phase 2：SGLang + DFlash 诊断矩阵（最低优先级）

固定：双 RTX 5090、TP=2、相同 target/draft、单请求、10K 总窗口、相同高考数学提示集和采样参数。GPU 可独占，允许做系统性扫参。

建议顺序：

1. **无投机基线**：vLLM 与 SGLang 各跑一次。先确定差距是投机解码造成的，还是基础 decode 已有差距。
2. **DFlash 深度扫描**：SGLang 扫 `k=5 / 8 / 10 / 12 / 16`；不要只测 k=16。vLLM 在当前 k=10 基线上继续扫 `k=12 / 15`。
3. **Attention backend 扫描**：优先核对 Qwen3.6 与 DFlash 的可用 backend；记录 Triton 与可用 FlashInfer/FlashAttention 方案。
4. **Mamba 状态策略扫描**：`extra_buffer`、`extra_buffer_lazy`、必要时 `no_buffer`；记录状态池、KV 池与 Decode TPS 的变化。
5. **CUDA Graph / 静态显存扫描**：仅在前四项定位后进行。一次只动 `mem-fraction-static` 或 `cuda-graph-max-bs-decode` 一个变量。

判定规则：

- 若无投机时 SGLang 已明显慢：优先检查 attention backend、GDN state、CUDA Graph 和 TP 通信。
- 若无投机接近、加 DFlash 后大幅落后：优先检查 draft 计算、verify window、接受长度和 replay/state cache。
- 若某改动 TPS 上升但数学正确率下降：直接淘汰，不作为候选生产配置。
- 若某改动 TPS 上升但 TTFT 或稳定性恶化：以“正确答案端到端耗时”决定是否保留，不按吞吐优先。

### Phase 3：Qwen3.8-27B 单卡可复现部署（231）

目标：先建立正确、稳定、可回滚的 5090 单卡数学解题服务，而不是追求 262K/1M 数字。

#### vLLM 基线

- 当前本地模型：`unsloth/Qwen3.8-27B-NVFP4`。
- 单卡官方思路：NVFP4 + FP8 KV，`--max-model-len 32768`；对官方 Inferact 单卡配方还需要 `--enforce-eager` 以避开 CUDA Graph 捕获 OOM。
- 首轮测试窗口：8K、20K、32K；每档都测试 reasoning on / low / off。
- 首轮投机：只测内置 MTP `num_speculative_tokens=3` 与 no-spec。

#### SGLang 基线

- 先用 NVFP4、FP8 KV、bfloat16 Mamba state、单请求。
- 分别测：no-spec、内置 MTP/EAGLE、DSpark。
- DSpark 使用独立 draft 后，额外记录 draft 显存、verify window、acceptance length 和 state pool；它不能只看输出 TPS。

完成标准：每个引擎至少有一条“可连续运行、能处理工具调用、可复现”的基线命令；性能数据要带上下文长度和 thinking 设置。

### Phase 4：Agent 真实负载与多模态（随后）

模型卡强调 Qwen3.8 的强项是长期 Agent、工具调用、视觉和视频；但你的近期业务是高考数学单请求，因此下一阶段要从“纯 token/s”走向“正确答案时间”，不急于投入并发服务或视频。

- 工具调用：验证 `qwen3_coder` parser，记录 tool-call 解析成功率。
- Reasoning：比较 `reasoning_effort=xhigh / medium / low` 的总时长、输出 token、任务成功率，而不是只比较单轮速度。
- Preserve thinking：对多轮 Agent 分别测试开/关，统计上下文增长、KV 命中与重复推理。
- 多模态：先图像，再短视频；把视觉 token 计入显存、TTFT 和上下文预算。

## 9. 高考数学单请求专项计划（当前执行版本）

### 9.1 北极星指标

生产候选配置的排序顺序如下：

1. **正确率不低于基线**。
2. 在满足第 1 条的配置中，**每道答对题的端到端耗时最短**。
3. 只有前两项接近时，才比较 Decode TPS、TTFT、显存余量和功耗。

建议定义三个正式指标：

| 指标 | 定义 | 用途 |
|---|---|---|
| Pass@1 | 单次生成的最终答案正确率 | 质量硬门槛 |
| Time-to-correct | 答对题目的端到端时间（含 TTFT、思考与最终答案） | 最终排序指标 |
| Decode TPS | 输出阶段速度 | 解释推测解码收益，不单独决定生产选择 |

### 9.2 评测集设计

不要用同一批题一边调参一边宣布正确率。建立两个固定集合：

| 集合 | 建议规模 | 目的 |
|---|---:|---|
| Calibration | 50 题 | 快速扫 k、backend、reasoning 设置 |
| Holdout | 150~300 题 | 只用于确认最终候选，没有参与调参 |

题目需覆盖：函数与导数、数列、立体几何、解析几何、概率统计、三角、向量、选择题、填空题和解答题。每题需要独立保存原题、标准答案、答案归一化规则、是否需要过程评分、难度标签与来源授权信息。

### 9.2.1 当前脚本的使用约束

脚本名包含 `concurrent`，但本阶段的产品目标是单请求速度。因此每一轮正式 benchmark 都必须显式保证：

```text
并发 = 1
单个请求独立计时
连接复用策略固定
关闭或固定重试逻辑
流式首 token 与最终结果均记录
```

已核对的字段映射如下：

| 所需信息 | JSONL / 脚本中的实际字段 |
|---|---|
| 唯一题目 ID | `id` |
| 原题文本 | `question` |
| 标准答案 / 参考解答 | `reference_answer`（当前是完整解答，不是统一的短最终答案） |
| 题型信息 | `math_type`、`tag`、`difficulty`、`grade` |
| 题目来源 | `source` |
| 模型完整输出 | 输出 JSONL 的 `model_output` |
| 最终答案 | 输出 JSONL 的 `final_answer_raw`，但**当前脚本没有填写** |
| 单题模型调用耗时 | `metadata.latency_seconds` |
| 批处理总耗时 | `metadata.total_elapsed_seconds`，包含排队，**不得用于单请求性能比较** |
| TTFT / 输出 token / 结束原因 | **当前脚本未记录，需补齐** |
| 判题结果与失败原因 | **当前脚本未实现，需另建判题环节** |

### 9.2.2 当前脚本的已验证行为

`run_model_tir_inference_concurrent.py` 的实际 CLI 参数和行为：

```text
--workers             总 worker 数，默认 8；本阶段必须设为 1
--tir_workers         仅 TIR 模式 worker 数；不设时回退到 --workers
--cot_workers         仅 COT 模式 worker 数；不设时回退到 --workers
--mode tir|cot        默认 tir；TIR 使用 TIRMathAgent，COT 使用无工具的 Assistant
--lang zh|en          默认 zh
--max-tokens          默认 8192
--limit               仅用于小样本冒烟，不用于最终结果
```

单请求基准命令的骨架应为：

```bash
python run_model_tir_inference_concurrent.py \
  --input ../data/math_qa_275_20260617.mineru.filled_reference_answer-v2.jsonl \
  --output ../data/model_outputs/<run-id>.jsonl \
  --api_base <endpoint>/v1 \
  --model <served-model-name> \
  --workers 1 \
  --mode <cot-or-tir> \
  --lang zh \
  --max-tokens 8192
```

每次运行必须使用新的 `<run-id>.jsonl` 输出路径。脚本会跳过同一输出文件中已有成功 `id` 的题目；复用旧输出文件会导致“看似测试完成、实际没有重新推理”。

### 9.2.3 计时口径：当前脚本可用与不可用的指标

| 指标 | 当前状态 | 单请求数学基准中的处理 |
|---|---|---|
| `metadata.latency_seconds` | 已有；覆盖 `bot.run()` 的请求到完整回答 | 当前的单题端到端主耗时 |
| `metadata.total_elapsed_seconds` | 已有；从批量提交时刻开始算 | 只用于排队诊断，workers=1 时后续题会持续累积，不能比较速度 |
| TTFT | 缺失 | 后续在流式循环收到第一个 delta 时写入 |
| 输出 token / Decode TPS | 缺失 | 后续从 usage 或 tokenizer 记录；没有它不能重新计算真实 Decode TPS |
| `finish_reason` / 截断 | 缺失 | 后续记录，避免把因 `max_tokens` 截断的错误答案当成模型能力不足 |

当前脚本每题都会新建一个 agent；`latency_seconds` 不包括 agent 构造开销，但对“同脚本、同模式、同 endpoint”的 A/B 仍是可比指标。若要衡量真实线上全链路，应在脚本增强后另记 client wrapper 开销。

### 9.2.4 正确率判定方案

当前 `reference_answer` 是完整参考解答，不能直接做字符串相等判断。应把题目拆成两条判定路径：

| 题目 | 首选判定 | 注意事项 |
|---|---|---|
| 选择题 / 填空题 | 从 `\\boxed{}` 或约定最终答案区提取后做规范化、符号等价判定 | 需要处理 LaTex、分数、根式、集合、单位与多解 |
| 解答题 / 证明题 | 先判最终结论，再使用盲评 rubric 或独立 judge 做过程判定 | 不可用“与参考解答文本相同”替代正确性 |

在调整 DFlash 的 k、runtime 或 backend 时，先固定 `--mode`。建议先分别建立两条质量基线：

```text
COT（无工具）Pass@1 与 Time-to-correct
TIR（TIRMathAgent）Pass@1 与 Time-to-correct
```

二者是不同推理工作流，不能混在同一条 k 扫描曲线中。最终选择“通过质量门槛且正确答案时间更短”的 workflow，再在该 workflow 内调 DFlash。

### 9.3 质量门槛

以当前双 5090 vLLM + DFlash k=10 作为质量基线。每个候选配置必须：

- 使用同一模型、同一 chat template、同一 system prompt、同一采样参数和同一最大输出长度；
- 在 holdout 上的 Pass@1 不低于基线；实践中可先设为“绝对下降不超过 1 个百分点”，再做人工复核；
- 不允许因最大输出长度过短而截断完整推理；把 `length` 截断率单独记录；
- 对选择/填空题做规范化答案匹配；对解答题优先记录最终结果正确性，再逐步加入过程评分。

### 9.4 立即执行顺序

1. 选定并冻结数学题集、prompt 模板和判题脚本。
2. 用 `--workers 1 --limit 10` 完成 COT 与 TIR 的小样本冒烟，并检查 `\\boxed{}` 提取、空输出和 `max_tokens=8192` 截断。
3. 增强脚本或新增后处理：写入 TTFT、输出 token、finish reason、最终答案提取和判题结果。
4. 用当前 vLLM + DFlash k=10 分别跑 COT 与 TIR 的 calibration，选出更适合高考数学的 workflow。
5. 在选定 workflow 下跑 200 题 holdout，得到 Pass@1 与 Time-to-correct 的零号基线。
6. vLLM 只扫 k=12、k=15；若准确率不降且 Time-to-correct 变短，则更新最优点。
7. SGLang 先选 **Low-Latency** 配方，跑 no-spec 基线；再做 DFlash / DSpark 分支实验。
8. 每次扫参后只保留同时通过正确率门槛和稳定性检查的候选。

### 9.5 当前不做的事

- 不先追求多用户高并发。
- 不先追求 262K / 1M 上下文。
- 不同时更换模型、量化、投机 draft 和 runtime 版本。
- 不以 acceptance rate 或服务端吞吐数字取代数学正确率。
