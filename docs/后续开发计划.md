# 后续开发计划

## 固定边界

CoT 思考模式是固定需求。隐藏思考原文，仅展示阶段和耗时。TIR 不在当前或未来范围：不引入 Python 执行器、代码沙箱、工具调用循环。页面和业务 API 使用 TypeScript，模型继续由 vLLM 提供。

## P1：部署到 231

- 当前先在本机运行、逐题验证使用体验；验证后再安排部署。
- 增加 Dockerfile 和 Compose，构建前端并由同一个 Node 服务提供页面和 API。
- 先检查空闲端口，再确定 Web 端口；保留现有模型服务的 8200 端口与运行参数。
- 题库只读挂载，历史目录独立持久化并备份；容器内模型地址通过环境变量配置，不能把 127.0.0.1 误当成宿主机模型服务。
- 增加模型连通性检查、优雅退出和健康检查；确认反向代理不缓存 SSE，超时时间覆盖长题推理。
- 明确局域网访问范围，需要多人使用时增加认证和请求权限控制。
- 验收：从另一台局域网机器运行单题、取消、查看历史，重启应用后记录仍在。

## P2：测试管理

- 历史结果导出 JSONL/CSV，正式解答导出 Markdown。
- 同一道题的多个运行并排比较；记录参数预设和提示词版本。
- 显示输入/输出 token 明细，只有接口明确提供时才展示思考 token 数量。
- 数据增多后增加历史分页和索引，必要时迁移 SQLite。
- 完善图片资源映射，区分缺图与可用图片；支持原题图/答案图预览。

## P3：题库质量

- 核对文件名 275 与实际 250 题的差异，明确是子集还是缺失数据。
- 审查 OCR 内容，尤其参考答案公式和结论；原始数据保留，修订版本单独记录。
- 补齐图片、建立图片文件与题号映射。
- 标记缺图题、疑似错题、答案不完整题，评测时可筛除。

## P4：可选批量与辅助评分

- 待个人逐题体验稳定后，增加批量任务、排队、进度、暂停/恢复和失败重试。
- 先固定并发 1 建立基线，再通过实测选择并发；不要让批量任务影响交互测试。
- 数值题可增加数学等价校验；证明题可引入辅助评分，但必须保留人工复核。
- 区分模型答错、参考答案错误、题目缺失与输出截断，避免混成同一“错误率”。

## P5：CoT 性能基线

- 固定题目集、提示词、模型/镜像版本、采样参数与输出预算。
- 统计正确率、失败率、首响应、思考阶段和总耗时；保留原始结果。
- 建立基线后再单独评估 CUDA Graph、量化、推测解码等服务侧改动。
- 任何模型服务优化都作为独立任务实施和回归，不因页面开发而修改正在使用的容器。
